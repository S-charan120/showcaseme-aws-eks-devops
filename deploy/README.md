# Kubernetes delivery and GitOps

## GitLab is the deployment source

The AWS delivery path uses GitLab CI and Argo CD. The public portfolio repository is on GitHub, but the Terraform GitLab OIDC trust and pipeline expect a GitLab project at `gitlab_project_path` (default: `S-charan120/showcaseme-aws-eks-devops`). Import or mirror the repository into that GitLab project before using the release pipeline.

The GitLab `.gitlab-ci.yml` validates, builds and publishes API/web images, then commits the two immutable image tags to `deploy/helm/showcaseme/values-aws.yaml`. Argo CD reads that GitLab project and reconciles the Helm chart. GitHub Actions validates the GitHub repository only; it does not deploy to AWS. A GitLab push mirror back to GitHub is optional.

API and web dependencies are installed with `npm ci` from committed lockfiles. Dependency changes should be made and reviewed as source commits, not generated by CI.

## GitLab CI variables

Set these in GitLab > Settings > CI/CD > Variables. Keep the AWS values protected and masked where supported; use `GITOPS_PUSH_TOKEN` as a masked, protected project access token with only `write_repository` scope.

| Variable | Source |
|---|---|
| `AWS_ROLE_ARN` | Terraform output `gitlab_ci_role_arn` |
| `AWS_REGION` | Terraform output `aws_region` |
| `ECR_API_REPOSITORY` | Terraform output `ecr_api_repository_url` |
| `ECR_WEB_REPOSITORY` | Terraform output `ecr_web_repository_url` |
| `GITOPS_PUSH_TOKEN` | GitLab project access token; Git write only, not an AWS credential |

The GitLab OIDC ID token audience is `sts.amazonaws.com`. Terraform restricts the trust policy to the configured GitLab project path, branch and audience. The ECR variables must contain full repository URLs (registry/account and repository name), not only repository names.

The publish job serializes ECR publication and checks whether each immutable `sha-$CI_COMMIT_SHA` tag already exists before pushing. The GitOps promotion job serializes edits to the Helm values file. For a protected default branch, configure the approved CI identity to push or change the promotion design to a merge-request workflow.

## Terraform output values and controller setup

Run these commands from the repository root after Terraform apply:

```bash
TF_DIR=infra/terraform
AWS_REGION="$(terraform -chdir="$TF_DIR" output -raw aws_region)"
CLUSTER_NAME="$(terraform -chdir="$TF_DIR" output -raw cluster_name)"
VPC_ID="$(terraform -chdir="$TF_DIR" output -raw vpc_id)"
ALB_CONTROLLER_ROLE_ARN="$(terraform -chdir="$TF_DIR" output -raw alb_controller_role_arn)"
CLUSTER_AUTOSCALER_ROLE_ARN="$(terraform -chdir="$TF_DIR" output -raw cluster_autoscaler_role_arn)"

aws eks update-kubeconfig --region "$AWS_REGION" --name "$CLUSTER_NAME"
kubectl get nodes -o wide
```

Install Argo CD following its [official installation guide](https://argo-cd.readthedocs.io/en/stable/getting_started/). Ensure the `argocd` namespace exists before applying the Argo CD Application CRs:

```bash
kubectl create namespace argocd --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f deploy/argocd/metrics-server.yaml
```

Install the AWS Load Balancer Controller after EKS is reachable. Install its CRDs using the official AWS instructions for the selected controller release, then install the chart using values from Terraform:

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update
helm upgrade --install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system --create-namespace \
  --set clusterName="$CLUSTER_NAME" \
  --set serviceAccount.create=true \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set serviceAccount.annotations.eks\\.amazonaws\\.com/role-arn="$ALB_CONTROLLER_ROLE_ARN" \
  --set region="$AWS_REGION" \
  --set vpcId="$VPC_ID"
```

The Cluster Autoscaler Argo CD Application contains sample cluster name, region and IAM role values. Replace them with the Terraform outputs before applying:

```bash
sed -i "s|showcaseme-dev|$CLUSTER_NAME|g" deploy/argocd/cluster-autoscaler.yaml
sed -i "s|ap-south-1|$AWS_REGION|g" deploy/argocd/cluster-autoscaler.yaml
sed -i "s|REPLACE_WITH_TERRAFORM_CLUSTER_AUTOSCALER_ROLE_ARN|$CLUSTER_AUTOSCALER_ROLE_ARN|g" deploy/argocd/cluster-autoscaler.yaml
kubectl apply -f deploy/argocd/cluster-autoscaler.yaml
```

Install Argo CD repository credentials for the GitLab project if it is private. For a public project, Argo CD can read it without credentials. Before applying the application, confirm that `deploy/argocd/application.yaml` points to the intended GitLab URL, `main` branch and `deploy/helm/showcaseme` chart path:

```bash
kubectl apply -f deploy/argocd/application.yaml
kubectl get applications -n argocd
kubectl get hpa -n showcaseme
```

## Initial release prerequisites

- Terraform has created VPC, EKS, RDS, S3, ECR, OIDC providers and IAM roles.
- The RDS and JWT values have been copied from the Terraform-created Secrets Manager secrets into Kubernetes Secret `showcaseme-runtime` (see [deployment runbook](../docs/deployment.md)).
- `values-aws.yaml` has the real ECR repository URLs, application IRSA role ARN, S3 bucket, AWS region and ACM certificate ARN.
- GitLab CI variables and OIDC trust match the configured Terraform values.
- The first eligible GitLab default-branch pipeline publishes both `sha-$CI_COMMIT_SHA` images and updates both Helm image tags. Confirm the GitOps commit and image tags before allowing Argo CD to sync.

Do not treat successful GitHub Actions validation as evidence that GitLab OIDC, ECR publication or an EKS deployment has run. Those steps require the external GitLab/AWS setup above.
